# Output File Improvement Plan

## Goal

Extend the Go output system along two independent dimensions:

1. **File generator** controls the output format.
2. **Destination** controls where the generated byte stream is stored.

The initial target combinations are:

| Generator | Local file | Amazon S3 | Azure Blob Storage |
|---|---:|---:|---:|
| Flat file | Yes | Yes | Yes |
| JSON | Yes | Yes | Yes |

Keeping these concerns separate avoids implementations such as `S3JSONWriter`,
`S3FlatFileWriter`, and `AzureJSONWriter`. A generator should work with every
destination.

```text
SourceLine -> Generator -> byte stream -> Destination
                  |                       |- Local file
                  |- Flat file            |- Amazon S3
                  `- JSON                 `- Azure Blob Storage
```

## Implementation Status

An Azure Blob destination has shipped, but as a narrower, more direct change
than the design below — the same precedent as the blob reader documented in
[`source-file-improvement.md`](source-file-improvement.md). See
`go/writer/blobwriter.go`, `render.go`, the `DestinationConfig` in
`writer.go`, the shared `go/azureauth` package, and
[usage.md](usage.md), §4.3, for the resulting configuration shape.
Concretely, this plan's proposals were **not** followed as written:

- No public `Generator`/`Destination`/`Upload` interface split —
  `AzureBlobWriter` implements the existing `Writer` interface directly, the
  same shape as `DefaultWriter`. The generation/storage separation exists but
  as an unexported `renderer` type (filename/header/row/footer templating and
  `uniqueKey` de-duplication, no I/O) shared by both writers.
- `DestinationConfig` is flatter than the `Local`/`S3`/`Azure` nested-pointer
  shape sketched in [Proposed Configuration](#proposed-configuration):
  `{Type, Path, URL, Auth}`, embedded in `OutputConfig` so the wire form stays
  flat (`type`/`url`/`auth` beside `filename`), mirroring the reader's
  `SourceConfig`. The output `url` is a container/prefix; the rendered
  `filename` is appended to it.
- Credentials are caller-supplied through the shared `azureauth.AzureAuth`
  struct (extracted from `go/reader` so source and destination can use
  different storage accounts) rather than assumed from the provider default
  chain only.
- Upload streams through an `io.Pipe` into the SDK's block-blob
  `UploadStream` as rows are pushed, not hand-rolled bounded block streaming
  with configurable concurrency — the SDK owns block sizing and concurrency
  internally. Memory use is not proportional to output size, matching the
  reader side. `End` closes the pipe (letting the SDK commit the block list)
  and waits for the background upload to finish; `Delete` called before `End`
  aborts the in-flight upload instead of committing then removing it.
- Known limitation, kept for now: the orchestrator's forced cleanup
  (`etl.cleanUp(force)`) always calls `output.End()` before `output.Delete()`,
  so on a mid-run failure the partial blob output is committed then deleted —
  the writer's abort path is never taken from that call site — and cleanup
  errors are discarded (`etl.Process` ignores the forced cleanup's return).
  If the commit succeeds but the delete then fails, a stray partial blob can
  remain with no error surfaced. Fixing this belongs with the
  [cleanup phase](#context-errors-and-cleanup) work (abort-aware cleanup and
  reported cleanup failures); see also the operational note in
  [usage.md](usage.md).
- Error reports remain local-only, and `Writer.Path()` keeps returning a local
  staging directory (OS temp dir for blob output) so the orchestrator is
  unchanged.
- S3, the JSON generator, `context.Context` threading, the `Result`
  `outputLocation` fields, and upload tuning remain unimplemented — the phased
  design below is still the reference for that future work.

## Motivation

The current `DefaultWriter` combines:

- filename, header, row, footer, template, and de-duplication logic;
- local filesystem creation and deletion;
- buffering, flushing, and closing an `os.File`.

This works for local output but makes cloud output unnecessarily coupled to the
file format. It also assumes that every result has a local path.

Direct cloud streaming is particularly useful in serverless environments:

- it does not depend on persistent local storage;
- memory remains bounded by upload buffer and concurrency settings;
- the upload can begin when the first valid row is produced;
- backpressure prevents unbounded buffering;
- the function context can cancel an incomplete upload;
- workload identity can be used instead of credentials in configuration.

## Proposed Configuration

`fileGenerator` selects the format. `destination.type` selects the storage
backend.

### Flat file to S3

```json
{
  "fileGenerator": "flat-file",
  "filename": "products_{LOC}.csv",
  "separator": ",",
  "destination": {
    "type": "s3",
    "bucket": "exports",
    "prefix": "daily",
    "region": "me-central-1"
  }
}
```

### JSON to Azure Blob Storage

```json
{
  "fileGenerator": "json",
  "filename": "products.json",
  "destination": {
    "type": "azure-blob",
    "container": "exports",
    "prefix": "daily"
  }
}
```

### Backward compatibility

An omitted destination should mean local output:

```json
{
  "fileGenerator": "flat-file",
  "path": "/var/tmp",
  "filename": "products.csv"
}
```

The existing empty or `"default-generator"` value can initially remain an alias
for `"flat-file"`. It can be deprecated separately if desired.

Secrets such as access keys and connection strings should not normally be part
of the ETL JSON. The implementations should use the standard AWS and Azure
credential chains so Lambda execution roles, Azure managed identities, local
profiles, and environment-based credentials work naturally.

## Proposed Design

### Generator

A generator transforms validated source lines into output bytes. It owns format
state but does not open files or contact cloud storage.

The exact interface may change during implementation, but the intended boundary
is:

```go
type Generator interface {
	Filename(*line.SourceLine) (string, error)
	Header(*line.SourceLine) ([]byte, error)
	Row(*line.SourceLine) ([]byte, error)
	Footer() ([]byte, error)
}
```

Generator responsibilities include:

- rendering the filename from the first valid row;
- rendering flat-file headers, rows, and footers;
- applying separators or row templates;
- tracking `uniqueKey` values when de-duplication is enabled;
- maintaining JSON document state, such as comma placement.

### Destination

A destination creates an upload session for one named object:

```go
type Destination interface {
	Start(ctx context.Context, name string) (Upload, error)
	Location(name string) string
}

type Upload interface {
	io.Writer
	Commit() error
	Abort() error
}
```

`Commit` finalizes a successful output. `Abort` performs best-effort cleanup
after a processing, cancellation, or upload failure.

Destination behavior:

- **Local:** create a buffered file; commit flushes and closes it; abort closes
  and removes it.
- **S3:** connect an `io.Pipe` to a multipart uploader; commit closes the pipe
  and waits for upload completion; abort cancels and aborts the multipart
  upload.
- **Azure Blob:** connect the stream to the block blob upload API with bounded
  buffers and concurrency; commit waits for completion; abort cancels the
  operation and performs applicable cleanup.

Cloud implementations must not issue one request per output row.

### Writer coordination

A coordinating writer combines one generator with one destination:

```go
generator, err := GeneratorFactory(config)
destination, err := DestinationFactory(config.Destination)
output := NewWriter(generator, destination)
```

It preserves the current lazy behavior:

1. No output session is created until the first valid row.
2. The first row determines the rendered filename.
3. The session receives the header, rows, and footer.
4. Successful processing commits the session.
5. Failed or invalid processing aborts the session.

Writes should honor destination backpressure. The writer must also retain an
asynchronous upload error and return it from subsequent writes or finalization.

## Generator Details

### Flat-file generator

Extract the reusable behavior currently in `DefaultWriter`:

- filename templating;
- configured header and footer;
- separator-based rows;
- template-based rows;
- metadata functions;
- `uniqueKey` de-duplication;
- existing newline behavior.

Golden tests should confirm that the extracted generator produces exactly the
same bytes as the current local writer.

### JSON generator

JSON must be emitted as a valid document without buffering the whole dataset:

```json
[
  {"id":"1"},
  {"id":"2"}
]
```

The generator can emit:

- header: `[`;
- first row: the encoded JSON object;
- later rows: `,` followed by the encoded JSON object;
- footer: `]`.

The zero-valid-row behavior must be chosen explicitly:

- preserve current lazy behavior and create no artifact; or
- create an empty JSON array, `[]`.

The recommended default is to preserve the current lazy behavior for
compatibility. An explicit option can support `[]` later if required.

## Result Model

The current result describes every output as local. Add destination-neutral
fields:

```go
type Result struct {
	OutputLocation string `json:"outputLocation"`
	OutputFilename string `json:"outputFilename"`

	// Deprecated compatibility fields for local output.
	LocalOutputFile     string `json:"localOutputFile,omitempty"`
	LocalOutputFilename string `json:"localOutputFilename,omitempty"`
}
```

Examples of `OutputLocation` are:

- `/var/tmp/products.csv`;
- `s3://exports/daily/products.csv`;
- an Azure Blob URL or another stable Azure location representation.

The existing local fields should remain populated for local destinations during
the compatibility period.

## Error Reports

Output destination and error-report destination should not be coupled through
`output.Path()`.

For the first version:

- keep error reports local;
- give the error report an explicit local path independent of output
  destination;
- document that a serverless caller must consume or upload the report if it is
  retained.

A later version can give error reports their own destination configuration.
That avoids implicitly writing error reports to the same bucket or container as
successful output.

## Context, Errors, and Cleanup

Cloud operations require `context.Context` throughout processing and
finalization. Add a context-aware entry point while preserving a compatibility
wrapper if needed:

```go
func Run(ctx context.Context, cfg Config) (Result, error)
```

Cleanup must be best-effort and must not stop after the first error:

- close or cancel the output upload;
- abort an incomplete cloud upload;
- finalize or remove the error report as appropriate;
- close the input reader;
- preserve the primary processing error while reporting cleanup errors.

Important failure cases to test include:

- filename rendering failure;
- failure starting an upload;
- write failure during processing;
- context cancellation;
- multipart or block upload completion failure;
- invalid ETL result requiring deletion;
- failure deleting an already committed object;
- empty input and all-invalid input.

## Factory Changes

Introduce two explicit factories:

```go
func GeneratorFactory(config OutputConfig) (Generator, error)
func DestinationFactory(config DestinationConfig) (Destination, error)
```

Suggested destination configuration:

```go
type DestinationConfig struct {
	Type  string `json:"type"`
	Local *LocalDestinationConfig `json:"local,omitempty"`
	S3    *S3DestinationConfig `json:"s3,omitempty"`
	Azure *AzureBlobDestinationConfig `json:"azure,omitempty"`
}
```

The final wire shape should avoid redundant nesting if possible. Configuration
validation should reject ambiguous combinations and report missing required
fields before processing begins.

## Implementation Phases

### Phase 1: Separate generation from local storage

- Introduce generator and destination/upload interfaces.
- Extract the existing flat-file rendering behavior.
- Implement the local destination.
- Adapt the coordinating writer and factory.
- Preserve existing configuration and output bytes.
- Add unit and golden compatibility tests.

Estimated effort: 1–2 days.

### Phase 2: Add the JSON generator

- Implement incremental JSON array generation.
- Define empty-output behavior.
- Test encoding errors, comma placement, and large streamed output.

Estimated effort: 1–2 days.

### Phase 3: Add S3

- Use the AWS default credential chain.
- Implement bounded multipart streaming and backpressure.
- Support bucket, prefix, region, content type, and optional upload tuning.
- Implement commit, cancellation, abort, and delete behavior.
- Add tests using a mocked client plus an optional integration test.

Estimated effort: 2–3 days.

### Phase 4: Add Azure Blob Storage

- Use the Azure default credential chain, with an optional connection-string
  compatibility mode if required.
- Implement bounded block streaming and configurable concurrency.
- Support container, prefix, content type, and optional upload tuning.
- Implement commit, cancellation, and cleanup behavior.
- Add tests using a mocked client plus an optional integration test.

Estimated effort: 2–3 days.

### Phase 5: Harden serverless behavior

- Thread `context.Context` through ETL execution.
- Make cleanup resilient to multiple simultaneous failures.
- Return destination-neutral result locations.
- Add cancellation, timeout, retry, and large-stream tests.
- Document Lambda and Azure Functions usage.

Estimated effort: 2–4 days.

## Overall Estimate

A production-ready implementation supporting flat-file and JSON generation
across local files, S3, and Azure Blob Storage is expected to take approximately
one to two weeks, including compatibility work and tests.

The critical first step is separating generators from destinations. Once that
boundary exists, additional formats and storage backends can be added without
multiplying writer implementations.
